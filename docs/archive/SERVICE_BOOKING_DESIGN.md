# 养老服务预约模块开发方向

适用项目：智享云家—社区智慧养老综合服务平台。

状态：已归档（2026-09-20）。预约模块三阶段开发已落地，原方向草案停止维护；当前实现与配置以[养老服务预约接口](../SERVICE_BOOKING_API.md)为准。以下保留原规划内容，不代表现行接口契约。

## 1. 目标与现有基础

围绕社区居家养老，提供助餐、助洁、陪诊、护理、康复等服务预约，形成“提出申请—社区确认—安排人员—执行服务—查看结果”的完整流程。

当前项目已具备基础认证、角色与社区校验、老人档案后端及管理端页面，可以复用。小程序本人身份绑定、家属授权、服务目录和履约能力尚未实现，需要按阶段补齐。

原有[业务系统设计](../SYSTEM_DESIGN.md)曾将预约容量与派单移出范围。本文提出重新纳入预约申请与人工安排，复杂容量管理和自动派单仍不纳入首期；开发范围确定后同步修订总体设计及接口契约。

## 2. 首期范围

| 功能 | 首期内容 |
|---|---|
| 服务目录 | 分类、服务项目、内容说明、时长、服务范围、参考价格、上下架 |
| 提交预约 | 选择老人、服务项目、期望时间、地址、联系人和必要备注 |
| 预约查询 | 列表、详情、处理进度、取消预约 |
| 社区处理 | 代老人预约、确认或拒绝、协调时间、人工安排人员 |
| 服务执行 | 工作人员查看本人任务，记录开始、完成和异常 |
| 操作记录 | 记录关键状态、时间、操作者及变更原因 |

首期采用“申请预约，人工确认”。提交成功仅表示社区已收到申请，页面提示“待社区确认”；社区确认后才形成明确的服务安排。

暂不包含在线支付、退款、短信通知、自动派单、复杂库存容量、周期预约、评价投诉及企业独立管理后台。参考价格仅用于展示，不生成支付状态。

## 3. 服务分类与差异信息

五类服务共用服务目录、预约单和状态流程，按类别补充必要字段，不分别建设五套预约系统。

| 分类 | 项目示例 | 差异信息 |
|---|---|---|
| 助餐 | 送餐上门、社区就餐 | 用餐日期、餐次、份数、必要饮食要求 |
| 助洁 | 日常保洁、专项清洁 | 清洁范围、服务地址、预计时长 |
| 陪诊 | 就医陪同 | 医院、就诊时间、集合地点、行动协助需求 |
| 护理 | 生活照护 | 照护内容、时长、必要注意事项 |
| 康复 | 康复指导、训练服务 | 服务地点、时长、是否需要先评估 |

护理、康复项目需区分生活服务与专业服务，并配置相应人员能力要求。预约模块不提供诊断或处方功能。差异字段使用明确类型和服务端校验规则，不以无限制自由文本代替结构化信息。

## 4. 多端职责与权限

| 入口 | 使用者 | 功能与数据范围 |
|---|---|---|
| 用户小程序 | 老人 | 浏览服务、为本人预约、查询本人进度、按规则取消 |
| 用户小程序 | 家属 | 为有效授权范围内的老人预约及查询 |
| 管理后台 | 社区人员 | 管理所属社区服务、代预约、确认申请、安排人员、处理异常 |
| 移动工作台 | 服务人员 | 查看分配给自己的任务和必要资料、记录执行结果 |

平台管理员仍需遵循明确的社区访问范围，不获得自动跨社区权限。首期由社区维护服务提供方和可安排人员，企业独立账号及后台后续设计。

身份、社区及对象权限由后端校验。老人本人账号必须与档案建立经核验的绑定关系；家属关系不自动等于授权，需校验授权范围、有效期及撤销状态。不能仅凭客户端提交的老人编号创建预约或读取资料。

## 5. 预约流程与状态

主流程：

```text
待确认 → 已确认 → 服务中 → 已完成
   ├──→ 已拒绝
   └──→ 已取消
          ↑
       已确认（符合取消规则时）
```

| 状态 | 含义与允许操作 |
|---|---|
| 待确认 | 已收到申请；社区确认或拒绝，申请人可取消 |
| 已确认 | 已明确服务时间和人员；可按规则取消，由被安排人员开始服务 |
| 服务中 | 已开始执行；记录结果或异常 |
| 已完成 | 已提交服务完成结果，保留历史，不允许继续修改预约内容 |
| 已拒绝 | 社区无法受理，必须填写原因 |
| 已取消 | 开始前按规则取消，记录操作者及原因 |

社区确认时填写实际服务起止时间及人员，检查人员资格、可服务范围和时间冲突。申请时间与确认时间分别保存；若时间变化，需记录与申请人协调的结果。

人员安排作为预约关联信息管理，不为每一次安排增加主状态。用户首期不直接修改已确认预约，调整由社区处理并保留记录。

服务异常记录原因和处理结果，不自动视为完成。无法继续服务的终止状态、处理权限及用户展示需在详细设计中确定，不允许使用“已完成”掩盖失败。

## 6. 数据与工程方向

继续沿用模块化单体、统一后端和现有前后端工程，不因角色数量拆分后端服务。

- 服务目录模块负责分类、项目、服务说明和上下架。
- 预约模块负责申请、确认、取消及人工安排。
- 履约模块负责开始服务、结果与异常；首期与预约保持明确关联，避免重复维护两套状态。
- 后端延续 api、service、mapper、domain 分层，事务和权限校验在服务层落实。

建议的数据实体如下，名称和字段在详细设计阶段确定：

| 实体 | 主要内容 |
|---|---|
| 服务分类 | 分类编码、名称、展示顺序、启用状态 |
| 服务项目 | 所属社区、分类、内容、时长、参考价格、提供方及人员要求 |
| 预约单 | 社区、老人、申请人、服务项目、期望与实际时间、联系人、状态、版本 |
| 人员安排 | 预约、执行人员、安排时间、调整记录 |
| 预约事件 | 操作者、动作、状态变化、原因、发生时间 |
| 服务结果与异常 | 开始结束时间、必要结果、异常原因及处理情况 |

预约单保存提交时的服务内容及参考价格快照，服务项目后续改名、调价或下架不改变历史记录。金额使用整数分，时间沿用现有接口规范。

关键约束：

- 提交使用请求编号实现幂等；同编号不同内容返回冲突，不重复创建预约。
- 状态变化采用版本校验和事务，防止重复确认、取消与开始服务相互覆盖。
- 人员时间冲突检查与安排写入必须具备数据库并发保护，不能只依赖前端或先查后写。
- 地址、电话及必要服务注意事项最小化采集，明确字段加密和读取权限；日志不记录敏感正文。
- 不允许为已归档老人新建预约；归档时已有未完成预约的处理规则需在详细设计中明确。
- 数据库结构使用后续 Flyway 迁移，不修改已发布迁移。

## 7. 开发阶段

### 第一阶段：服务目录与社区代预约

复用老人档案，完成目录管理、后台代预约、申请查询、确认拒绝、取消和人工安排。补充最小的服务人员可安排信息及权限约束。

交付目标：社区人员能够在后台完成一笔预约的创建和安排，查询完整处理记录。

### 第二阶段：老人本人预约

补齐正式用户认证接入和账号档案绑定，完成小程序服务列表、详情、预约表单、我的预约及取消入口。已核验的本人资料可预填，减少老人输入。

交付目标：老人能够提交真实申请并查看社区处理结果，不使用模拟身份或开发账号代替正式身份校验。

### 第三阶段：家属代预约与工作人员执行

补齐家属授权，提供获授权老人选择入口；建立工作人员任务列表、详情、开始服务、完成记录和异常处理。

交付目标：打通申请、安排、执行、结果查询的多方协同流程。

三个阶段共同组成首期模块，不将仅有预约表单视为模块完成。

## 8. 验收重点

本节为人工验收标准：AI 开发交付不执行本节验收，仅在用户明确要求时开展。

- 五类服务能够按各自必填信息提交、校验和展示。
- 预约状态按规则转换，拒绝、取消及异常有明确原因和记录。
- 重复请求不产生重复预约；并发确认、取消和人员安排不会产生冲突结果。
- 覆盖老人本人、有效与失效家属授权、跨社区访问、非本人任务访问等权限场景。
- 服务下架、人员不可用、档案归档、时间过期、版本冲突等情况返回明确中文错误。
- 由人工在专用测试库验证数据库迁移及并发安排，H2 结果不作为 MySQL 结论。
- 由人工对修改后的前端执行实际页面验证；小程序专有能力由人工在开发者工具及真机验证。
- 接口、数据库和配置契约随实现更新，明确区分实际验证结果与环境限制。

## 9. 详细设计前需确定的规则

1. 可预约日期范围、提前预约时长、取消截止时间。
2. 不同服务的时长、餐次与数量限制，以及参考价格展示方式。
3. 确认时是否必须指定具体人员，助餐是否允许按团队安排。
4. 时间协调的确认方式，以及改期和重新安排的限制。
5. 服务中止、无人履约、人员请假等异常的最终状态和处理权限。
6. 老人档案归档、家属授权撤销后，已有预约的处理和可见范围。
7. 服务结果由工作人员提交即完成，还是需要社区复核。

这些规则在详细设计阶段落实为接口、状态转换和验收用例；本文不预设已经获得确认的业务参数。
