# 健康记录与独立健康授权开发方案

状态：待评审草案。方案确认后开始业务开发，本文不代表已实现的接口或数据库结构。

## 1. 目标与范围

在现有老人档案、微信登录、本人绑定和服务预约基础上，建立日常健康测量记录功能。老人能够记录和查看自己的测量结果，家属经独立授权后查看，指定社区人员经授权后协助录入。

| 本期功能 | 具体内容 |
|---|---|
| 四类测量 | 血压、心率、体重、血糖的手工录入 |
| 记录查询 | 分页列表、详情、测量时间、来源、当前有效版本 |
| 数据更正 | 填写更正原因，保留旧版本；错误记录可作废 |
| 趋势查看 | 按指标与日期展示原始测量点，血糖按场景区分 |
| 独立健康授权 | 老人本人授予家属只读或指定社区人员协助录入权限 |
| 社区协助 | 仅处理本人获授权老人，并限制为自己录入的记录 |

本期不接入设备、医疗附件、过敏史及病历管理，不提供医学正常范围、诊断、预警或用药建议；支付、短信和求助投递继续保持原有范围。

本期采用固定的四类指标与明确字段，不建设通用指标配置平台、通用权限引擎或新的微服务。

## 2. 与当前工程的关系

- 后端沿用 Java 21、Spring Boot、Spring Security、MyBatis-Plus 和 MySQL；新增结构采用下一个未使用版本的 Flyway 迁移，当前预计为 V4。
- 复用会话、CSRF、账号状态与社区校验，以及 `elder_account_binding` 的本人身份事实。
- 新建独立 `HealthAccess`，不调用 `BookingAccess.elder()` 判断健康权限。现有预约查询允许社区管理角色访问，这个规则不能移植到健康模块。
- `booking_grant` 继续只控制预约。新建独立健康授权，已有预约授权不会自动升级。
- 健康接口使用 `/api/v1/health/**`。现有 `/api/v1/elders/**` 在安全过滤器中限管理角色，直接在其下新增移动端健康接口会受到错误的角色限制。
- 后端在 `health` 中维护记录与规则，`consent` 中维护健康授权；均按 api、service、mapper、domain 分层，事务位于 Service，复杂权限查询使用 MyBatis XML。
- 移动端接入已有“健康”导航；管理端接入已有 `/health` 占位路由。健康授权与“账号与预约授权”在交互和接口上明确区分。

## 3. 建议确认的业务规则

以下为本方案推荐默认值，评审通过后据此实现。

| 决策 | 推荐规则 |
|---|---|
| 谁能授予健康权限 | 已核验绑定的老人本人在线明确同意；家属、社区和平台管理员不能代替老人授予 |
| 家属可见范围 | 授权有效时可查看全部当前健康记录及趋势，含授权前记录；同意页面明确说明 |
| 社区协助范围 | 指定 `COMMUNITY_OPERATOR` 可以新增，并查看、更正或作废自己最初录入且尚未由老人接管的记录；不能读取其他人录入的记录或完整趋势 |
| 记录更正 | 老人可以更正或作废自己的档案中的记录；社区人员还需具备当前有效授权且满足记录归属 |
| 历史旧值 | 首期仅老人本人可查看完整历史版本；家属查看当前有效版本及是否更正的标识 |
| 授权期限 | 默认 30 天，可选择 7、30、90、365 天，到期需老人重新同意 |
| 代理与线下委托 | 暂缓监护代理、纸质委托及管理员代授权，未完成本人绑定的老人不能在线开通本模块 |

“协助录入”在同意页面完整描述为“新增、查看和更正该人员录入的记录”，不将其解释为全档案读写权。社区人员不能因曾经录入而保留永久访问权限。

## 4. 权限与授权生命周期

| 身份 | 当前记录 | 趋势 | 新增 | 更正、作废 | 授予权限 |
|---|---|---|---|---|---|
| 已有效绑定的老人本人 | 本人全部 | 本人全部 | 是 | 是 | 是 |
| 获健康只读授权的家属 | 获授权老人全部 | 是 | 否 | 否 | 否 |
| 仅有预约授权的家属 | 否 | 否 | 否 | 否 | 否 |
| 获协助授权的社区人员 | 仅本人原始录入且未被老人接管 | 否 | 是 | 仅本人原始录入且未被老人接管更正 | 否 |
| 无健康授权的社区人员 | 否 | 否 | 否 | 否 | 否 |
| 服务人员、平台管理员及其他角色 | 否 | 否 | 否 | 否 | 否 |

所有接口同时检查有效账号、角色、社区、本人绑定或明确授权及记录归属；社区、账号和操作者由服务器确定。角色不符返回 403，对象不在范围内与不存在均返回统一 404。

授权绑定到具体老人、具体受权账号和明确范围，不授权给整个社区。范围固定为 `FAMILY_READ`、`COMMUNITY_ASSIST`，分别只适用于 FAMILY 和 COMMUNITY_OPERATOR。

授权选择复用已有核验账号信息。首期通过受权人主动提供的账号编号精确查找，返回同社区、允许角色的最少身份信息，限制查询频率，不开放全社区成员目录；已有授权对象可作为候选快捷项。候选人信息不构成授权，最终仍由老人核对对象并明确同意。

授权撤销或到期后，后续请求停止提供记录、详情、趋势及原始代录记录；已经提交的健康记录继续保留。重新授权产生新的授权事实，不覆盖旧授权历史。

本人绑定停用、受权账号停用或社区不匹配时停止相应访问。本人绑定重新启用后，不自动恢复此前第三方健康授权；授权同时关联绑定编号和版本，需重新同意，不能仅检查当前绑定是否启用。

老人档案归档后停止新增、更正及第三方访问，有效绑定本人可只读历史和撤销授权。归档时撤销有效健康授权，恢复档案后由本人重新授予；这需要与现有归档服务同步处理。

首期不引入授权结果缓存。每次请求读取当前授权；撤销完成后发起的新请求必须拒绝。撤销前已经返回到终端的信息无法远程收回。

## 5. 记录与趋势规则

### 5.1 测量字段

| 类型 | 强类型内容 | 固定单位 |
|---|---|---|
| 血压 | 收缩压与舒张压成对提交，同一测量时间 | mmHg |
| 心率 | 一个整数值 | 次/分钟 |
| 体重 | 一个定点小数值 | kg |
| 血糖 | 一个定点小数值，以及空腹、餐前、餐后、随机或未说明场景 | mmol/L |

每条记录保存测量时间、系统录入时间、原始录入人及录入方式。来源固定为手工，方式由服务器区分本人录入和社区代录，不允许客户端伪装医疗机构来源。

服务端限制格式、小数精度、字段组合、存储上限与未来测量时间；这些是输入约束，不是医学正常范围。允许相同时间出现不同测量，不以“老人＋指标＋时间”强行去重。

### 5.2 更正与作废

- 一条逻辑记录有多个不可覆盖的版本，列表及趋势只使用当前有效版本。
- 更正要求填写原因并携带读取时的版本；冲突返回 409，提示刷新。
- 原始录入人、创建时间及归属不可修改；每次更正另记操作者和时间。
- 指标类型不能在更正时改成另一类型；录错类型通过作废原记录并新建处理。
- 老人更正或作废社区代录记录后，该记录由老人维护，原代录人员不能继续读取正文、更正或作废，也不能读取旧版本；其可见列表排除该记录，直接请求按不可访问对象处理。保留原始来源标识，避免把老人新增内容暴露给原代录人员。
- 作废不物理删除，作废记录不进入趋势。首期不提供作废恢复，需重新录入。

### 5.3 趋势查询

默认提供近 7、30、90 天，服务端限制单次最长 90 天。使用测量时间排序并显示单位、来源和时间；血压两条线对应同一测量点，血糖必须按场景筛选，不混成一条序列。

首期展示原始有效测量点，不计算风险评分或医学结论。查询设定明确点数上限，超限返回“请缩小日期范围”，不静默截断或伪造缺失点。无数据展示“暂无记录”，单点展示数值，缺失数据不显示“健康正常”。

时间接口使用含时区 ISO 8601，数据库存 UTC，日期筛选和页面显示以 Asia/Shanghai 为准。

## 6. 数据结构与一致性

| 拟新增实体 | 职责 |
|---|---|
| `health_record` | 逻辑记录、社区与老人、指标、原始录入人、本人接管标记、当前版本及状态、当前测量时间 |
| `health_record_revision` | 每版测量内容密文、更正原因密文、操作者、时间及版本号 |
| `health_grant` | 老人、受权账号、固定授权范围、有效期、撤销信息、绑定编号与版本、同意文案版本 |
| `health_event` | 记录写操作及敏感访问的元数据，不保存健康正文 |
| `health_mutation_request` | 写请求去重、规范化请求摘要、结果标识与版本，不存明文健康内容 |

测量内容在 API 和 Java 中使用固定 DTO，经校验后加密存储，不设计可任意扩展的字段字典。用于社区、老人、指标和时间查询的最小元数据保留索引；查询范围受限后在服务端解密，避免全表解密。

沿用现有 AES-GCM 加密方向，但健康域使用独立派生上下文；附加认证数据包含社区、老人、记录和版本，防止跨对象替换。具体配置在开发时明确，不修改既有档案或预约密文格式。加密请求摘要使用 HMAC，不能对小范围健康数值直接做无密钥哈希。

创建、更正、作废和授权写操作携带 `requestId`。数据库唯一约束区分社区、操作者、操作类型和请求编号；相同编号相同请求返回原操作结果标识，不重复写入，同编号不同内容返回 409。重试同样先核验当前权限，不能通过去重结果绕过撤销。

记录更新使用期望版本条件，并将版本新增、当前指针更新、事件和请求编号保存放在同一事务中。健康写操作、授权变化及关联归档沿用当前社区行锁和固定锁顺序，避免在同一事务外先判断后写入。当前规模接受按社区串行写入，后续有实际吞吐需求再细化锁范围。

健康响应使用 `Cache-Control: no-store`。正文不进入日志、本地持久化或 URL；注销、切换老人、页面退出和权限失效时清空内存数据，页面回到前台重新核验，不承诺远程删除截图。

## 7. 接口边界草案

路径均以 `/api/v1` 为前缀；仅为拟定契约，实施时在独立 `HEALTH_API.md` 中记录最终字段。

| 方法与路径 | 职责 |
|---|---|
| `GET /health/elders` | 返回本人、获授权家属或社区可协助的老人及允许动作 |
| `GET /health/elders/{elderId}/records` | 按权限、类型和时间分页查询当前记录 |
| `POST /health/elders/{elderId}/records` | 本人或获授权社区人员新增测量 |
| `GET /health/records/{recordId}` | 核验对象范围后读取当前详情 |
| `POST /health/records/{recordId}/corrections` | 按版本追加更正 |
| `POST /health/records/{recordId}/void` | 按版本作废记录 |
| `GET /health/records/{recordId}/revisions` | 本人查看历史版本 |
| `GET /health/elders/{elderId}/trends` | 本人或获只读授权家属查询趋势 |
| `GET /health/grants` | 查看本人授予或当前账号收到的健康授权 |
| `POST /health/grant-recipients/resolve` | 本人精确核对受权账号，仅返回必要身份信息，不产生授权 |
| `POST /health/grants` | 本人授予权限，包含具体对象、范围及有效期 |
| `POST /health/grants/{grantId}/revoke` | 本人撤销或受权人主动放弃；不能因此操作其他授权 |

列表和详情从同一权限规则构造查询，不先返回全量再在前端过滤。基础资料只输出选择老人必需的信息，不复用管理端完整档案响应。

## 8. 页面与组件方向

继续采用 Composition API、`<script setup lang="ts">` 和现有请求封装，不升级主要依赖。

| 页面或组件 | 单一职责与数据交互 |
|---|---|
| 移动健康入口 | 装配老人选择、指标、列表和趋势，按服务端能力展示入口 |
| `HealthRecordForm` | 接收指标及初始值，提交规范化表单事件；不直接请求接口 |
| `HealthRecordList` | 接收记录及分页状态，发出详情、翻页等事件 |
| `HealthRecordDetail` | 展示当前内容、更正标识及允许动作，触发更正或作废 |
| `HealthTrend` | 接收类型、单位和有序测量点，展示趋势及可阅读数值 |
| `HealthGrantPanel` | 展示独立授权、范围与期限，发出授予和撤销事件 |
| 管理端健康页面 | 只展示当前账号有协助授权的老人及本人代录记录 |
| `useHealthRecords` | 管理请求、选中老人、分页、更正冲突及内存清理 |

两端共享接口语义和字段约定，不强行共享依赖不同组件体系的页面。老人端延续大字号、清晰标签和少输入；图表同时提供数值信息，不以颜色作为唯一表达。

## 9. 实施与提交节点

方案确认后创建 `codex/health-records` 分支，按完整目的分别提交到本地 Git。提交只包含本模块改动，保留用户同期修改；远程推送范围尚未确定，不自动合并。

| 节点 | 交付内容 | 建议提交消息 |
|---|---|---|
| 1 | 迁移、独立授权、健康记录与更正、加密、权限及接口契约 | `feat(health): 实现健康记录与独立授权接口` |
| 2 | 老人录入、查询、更正和授权管理，家属只读与趋势 | `feat(mobile): 接入健康记录与家属健康授权` |
| 3 | 社区授权代录、本人录入记录查询和更正 | `feat(admin): 支持授权范围内的健康协助录入` |
| 4 | 实际发现的跨模块遗漏修复、最终契约同步与方案归档 | 按最终改动使用 `fix(health)` 或 `docs(health)`，不为凑节点制造改动 |

每个代码节点仅补充和运行相关最小单元测试，并进行一次对应编译或构建：后端针对新增单元测试执行 Maven test，前端只构建当前修改的一个目标。遵循 AGENTS.md，不运行完整 verify、lint、format:check 或双端完整构建。

模块完成后将本文移入 `docs/archive/` 并登记；长期维护 `HEALTH_API.md` 和总体设计，不以草案代替当前行为。

## 10. 评审关注点

请重点确认第 3 节的规则：本期由老人本人在线授权；家属授权覆盖既有记录；社区只能维护自己的代录记录；线下代理暂缓。确认这些边界后，后续字段和组件细节按本方案自主实施。
